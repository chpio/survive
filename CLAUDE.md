# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A top-down 2D survival game built with Bevy 0.20, Avian2D 0.8 physics, and `bevy_ecs_tiled` 0.15 (with the `avian` feature) for Tiled maps. These three must stay on mutually compatible versions; check with `cargo outdated --root-deps-only`.

## Commands

```sh
cargo run          # run the game (assets are loaded from ./assets, hot-reloaded via file_watcher)
cargo check        # fast type check
cargo clippy       # lint
cargo fmt          # format
cargo tracy        # release build with Bevy's spans sent to the Tracy profiler (alias in .cargo/config.toml)
```

`cargo tracy` enables `bevy/trace_tracy`: every system and schedule becomes a span, which the Tracy profiler (version 0.14, matching the bundled client) shows per thread once it connects to the running game. It shows each system's own run time, which the HUD's "Performance" view doesn't measure. The spans slow down the frame a bit.

Tests live in `tests/` (never inline) and run with `cargo test`; filter with `cargo test --test it enemy`. They form a single test binary `it` (`autotests = false`; `tests/main.rs` only declares the modules), so the game and its dependencies are linked once; the lib and binary have no test targets of their own (`test = false` in `Cargo.toml`). All tests run as threads of one process, so they must not share process-wide state (statics, environment variables, the current directory). Game code is in the `survival` lib crate (`src/lib.rs`) so tests can use it; `src/main.rs` only builds the `App`. `tests/common.rs` builds a headless physics app; `common::app_with` takes extra plugins, which can't be added once the app is finished.

Build notes:
- Bevy uses `default-features = false` with a hand-picked feature list in `Cargo.toml`. The commented-out lines mirror Bevy's default features. If a Bevy type or plugin is missing, the feature that provides it is probably commented out.
- Gizmos (physics debug outlines, flow field arrows) need both `bevy_gizmos` and `bevy_gizmos_render`; without the latter they are recorded but never drawn.
- The `dynamic_linking` feature is always on, including in release builds.
- Dev builds use `opt-level = 1` for the crate and `3` for dependencies.

## Architecture

- `src/main.rs` builds the `App`: window/image settings, FPS overlay, Tiled + Avian plugins (with `Gravity::ZERO`, top-down; physics runs at Bevy's fixed 64 Hz and interpolates all bodies' `Transform`s in between, so code reading `Transform` sees positions up to one step behind the physics), and the game object plugins. `startup` spawns the camera, the player, and the `TiledWorld`.
- `src/objects/` holds one module per game object. Each module defines a marker `Component`, its systems, and a `pub struct Plugin` that registers them. New objects follow this pattern and get added to the plugin tuple in `main.rs`.
- The world (`src/world.rs`, concept in `docs/welt.md`) consists of the Tiled maps in `assets/world.world`; bevy_ecs_tiled only spawns those that the area of `TiledWorldChunking` around the camera touches and despawns the others with all their children. `world::update_chunking` keeps that area at least as large as the view and `world::MIN_LOADED_DISTANCE` (what the flow field and the sight need around the player). Each loaded map gets a `MapArea`; the flow field and the sight keep a raster of the map's colliders on the map's entity (`world::MapRaster`, built by `world::rasterize` when the map is loaded and again only when one of its colliders changes), so it disappears with the map. Both work on one raster of 4 px cells over the whole world (`src/cells.rs`), on which all maps lie since they are placed in whole tiles. Enemies have no parent; `enemy::despawn_outside_maps` removes those that stand on no loaded map (with `UNLOAD_MARGIN`) once a second. Items stay when their map is unloaded.
- `src/flowfield/` keeps one grid per clearance in `flowfield::CLEARANCES`; enemies of any radius (`Enemy::radius`) use the grid with the smallest clearance at least their radius. Cells closer than the clearance to a non-sensor collider of a map (they are all static) are blocked, and a Dijkstra search from the player's cell gives each free cell its walking distance. Each map's `flowfield::Obstacles` stores the distance from each cell to its closest obstacle, over the map and a margin of the largest clearance, so obstacles at a map's edge also block the neighbor map's cells. The distances only cover a square window of a fixed size around the player's cell (`FLOW_FIELD_RADIUS`), which moves along with each search; its blocked cells are put together from the loaded maps' obstacles then, and cells outside all loaded maps are blocked. When a map is loaded, unloaded or rasterized again, all grids forget their target and search again. Only the grids used by awake enemies, requested by a `flowfield::Request` (spawners that need walking distances before their enemies exist) or shown by the debug overlay are computed; the others forget their target until they are needed again. `FlowField::walking_distance` and `Grid::reachable` give the distances in px. Blocked cells within the clearance around the player that aren't inside a collider stay walkable, so the player is reachable while standing closer to an obstacle than the clearance. Enemies with a free line of sight walk straight at the player, the others follow the field via `FlowField::direction` and steer away from each other while their personal spaces (`enemy::Separation`, radius and strength per enemy) overlap. `flowfield/debug.rs` draws the window of one grid as an overlay (blocked cells, distances, field directions); `FlowFieldDebug::cycle` switches between the grids.
- Movement is force-based (`src/movement.rs`). Systems set a `DesiredVelocity` on Avian bodies (player and enemies: `RigidBody::Dynamic` with `Mass` and `Strength`) instead of changing `Transform` or `LinearVelocity` directly. In `FixedUpdate`, a spring towards an anchor moving at that velocity applies a force limited by `Strength`, so heavier and stronger bodies win when pushing each other. After the desired velocity changes, the body first changes its velocity straight to it at full strength (and the anchor starts again at the body), so it neither overshoots nor snaps back when starting or stopping. Avian runs with `movement::LENGTH_UNIT` (16 px, one tile) and `movement::CONTACT_TOLERANCE`, in `main.rs` and `tests/common.rs` alike; with a larger contact tolerance, bodies sliding along the map's triangulated colliders get pushed away at corners. Bodies are built with `movement::body`, have no friction (so they slide along obstacles instead of sticking at corners) and never rotate; an enemy's visible `enemy::Body` is a child that turns towards its `enemy::Heading` (the direction its navigation wants to walk, unaffected by knockback; `enemy::face_heading`, limited by `TURN_SPEED`), so other children like health bars stay upright. All enemies share one unit-circle mesh and their materials (`EnemyAssets`), scaled to their radius. The camera follows the player's `Transform` and keeps its own z.
- Combat (`src/combat/`): units with `Health` and an `Attack` hit every opponent whose collider is within the attack's reach once per cooldown (the player all enemies around it, an awake enemy the player). A hit deals damage and knocks the target back with an impulse, so lighter units fly further. Dead enemies are despawned; when the player dies, all enemies are removed and the player is healed. `player::combat()` and `Enemy::combat` hold the values. `combat::health_bar` draws sprite bars above damaged units and is kept apart from the logic, since it needs rendering.
- The HUD (`src/ui/`) is a Dioxus Native document (Blitz, painted with Vello) rendered into a fullscreen image. Its styles are in `assets/ui/style.css`, loaded as a `Stylesheet` asset and hot-reloaded like the other assets; the HUD stays empty until it is loaded. The document has no user-agent stylesheet, so every element starts with CSS's initial values (`display: inline`, unsized checkboxes, visible `<style>` text); the base section at the top of `style.css` sets what the HUD's elements need, and new kinds of elements may need an entry there. `sync_state` writes the game state into one `hud::State` signal and handles the `hud::Action`s the HUD sends back over a channel. The HUD is only painted and rendered again after a mouse button or touch, a state change, a resize or a redraw request from Blitz (which also covers mouse moves that change the hover state); anything else that should change its look (e.g. animations) has to set `needs_paint`. On a window resize, `ui::resize` invalidates every node's layout cache and marks its overflow for recomputation; Blitz does neither on its own, which left centered text misplaced and, after the window grew, the HUD outside the area hit tests reach. Blitz gets all mouse input and touches (as pointers with a finger id; winit 0.30 has no pen API: under X11 pens arrive as mouse input, under Wayland not at all, see `TODO.md`); where the topmost element or an ancestor has the class `blocks-pointer` (`ui::blocks_pointer`), the picking backend `pick_hud` reports a hit on the HUD's image (`ui::Hud`) above the sprites, so picking in the game world only happens elsewhere (`docs/ui-events.md`). Bevy's own `ui_picking` is off, since it would hit the fullscreen image everywhere.
- Items (`src/items/`, concept in `docs/items.md`): each item is an entity with `Item(ItemId)`, stackable ones also have a `Stack` count. Item types (name, weight, stackable, placeholder color) come from `assets/items.ron`, hot-reloaded and copied into the `ItemDefinitions` resource, so tests can insert it directly. On the ground, an item shows a `Sprite` at its `Transform` and is `Pickable`; held, it is hidden (`Visibility::Hidden`, not by removing the sprite, since Bevy draws sprites as meshes it adds along with them and doesn't remove with them), has no `Pickable` and has the relationship `HeldBy(owner)`, mirrored by Bevy in the owner's `Inventory`. The `PickUp` and `DropItem` messages move items between ground and owner, merging stacks of the same type on pickup and splitting stacks when dropping part of them. `items::Plugin` holds that logic, `items::definitions::Plugin` the asset loading and `items::input::Plugin` the player's input (click to pick up within `PICKUP_REACH`, hover highlight, debug key), so tests only need the first.
- Sight (`src/sight/`, concept in `docs/sicht.md`): colliders with `BlocksSight` are rasterized into each map's `sight::OpaqueCells`. Around the player's cell, `Sight` keeps a mask of how visible each cell is (in `SIGHT_RADIUS`, fading out, nothing behind opaque cells; computed by recursive shadowcasting, since letting each cell inherit from its neighbor towards the player snaps shadow edges to 45° steps), in a square window that moves with the player and is only computed again when the player changes cells or the loaded maps change. The window's opaque cells are put together from the loaded maps then; outside of them, nothing blocks the sight. `sight::render` writes it into a linearly filtered texture that `SightMaterial` (shader `assets/shaders/sight.wesl`) samples around each pixel's world position, blurred over `render::BLUR`: enemies use it so only their parts in sight are drawn, and a large dark rectangle between items and units uses it inverted to darken everything outside the sight. Health bars of enemies are hidden while their middle isn't in sight. `Sight::sees` tells whether any part of a circle is in sight; sleeping enemies wake up by it, and spawners use it to stay out of sight.
- Spawning (`src/spawning/`, concept in `docs/spawnen.md`): sources decide what spawns where and send `enemy::SpawnEnemy` (enemy, position, whether it starts asleep), which `enemy::spawn_enemy` turns into an entity. An `enemy::Asleep` enemy stands still, doesn't attack and doesn't count for the flow field; `enemy::wake_and_sleep` wakes it once the player sees any part of it and lets awake enemies further than `DEACTIVATION_RADIUS` (400 px, beyond the flow field's 320 px, where awake enemies walk straight at the player) fall asleep where they stand. `spawning::ambush`: an object layer in Tiled with trigger zones (`type="ambush_trigger"`, `AmbushTrigger`) and spawn points (points with `type="ambush_spawn"` and the properties `radius`, `count`, `delay`; `SpawnPoint`); the layer's `spawn_points` limits how many are used. The player touching a zone marks all zones of the layer `Triggered` and requests the grids; once a point's delay is over and its grid is computed, it is used if its enemies are out of sight and at least `ambush::MIN_DISTANCE` away to walk, the closest first, and skipped otherwise. `spawning::out_of_sight::SpawnOutOfSight` places an enemy where the player doesn't see it, at a walking distance of 120–250 px, preferring places close as the crow flies (behind obstacles).
- Settings (`src/settings.rs`): the `Settings` resource (VSync, fullscreen, camera zoom) is the only source of truth. It is loaded from `settings.ron` when the plugin is built (so the window opens in the right mode), applied to the primary window and the 2D camera's projection scale whenever it changes, and saved then. The file lives next to the executable (`target/debug/` under `cargo run`). Escape toggles the `Menu` state; while it is `Open`, `Time<Virtual>` is paused, which stops physics and everything driven by game time. The HUD shows the menu and sends the whole changed `Settings` back as a `hud::Action`.
- `src/perf.rs` measures the frame time and, with marker systems before and after Avian's sets, the wall time of the physics for the HUD. Wall time between marker systems includes waiting for unrelated systems with conflicting access, so it is no measure for single game systems; use `cargo tracy` for those.

### Tiled map → ECS

- `assets/world.world` places the maps (`map.tmx` and the test map `map_east.tmx` east of it, 16×16 tiles, tileset `assets/grass_biome.tsx`); `startup` spawns it as a `TiledWorld` at the origin. Sizes and positions in the `.world` file must be whole tiles. The world's anchor is `TopLeft`, so a map's position in the game is its position in the `.world` file with y negated, as long as no map has a negative x. The player starts at `player::START` on `map.tmx`. `map_east.tmx` has a test ambush ("Hinterhalt Brücke" in the group layer "Hinterhalte") at the end of the land bridge.
- Settings on the world entity (`TilemapRenderSettings`, `TiledMapLayerZOffset`, `TiledPhysicsSettings`) are copied to each map by bevy_ecs_tiled, and `TiledEvent`s bubble up from the maps to the world through `ChildOf`, so the observer below sits on the world.
- Colliders defined in the tileset or map are created by `TiledPhysicsPlugin`. An observer on `TiledEvent<ColliderCreated>` makes each one `RigidBody::Static`, then reads the object's Tiled `type` (or the tile's type as a fallback) to attach game components. For example, `type="well"` (tile 197 in the tileset) becomes `Well + Sensor + CollisionEventsEnabled`, and `type="ambush_trigger"` an `AmbushTrigger` sensor. Objects without a collider (points) go through a second observer on `TiledEvent<ObjectCreated>`, e.g. `type="ambush_spawn"`. Both events know the object's layer (`layer_entity`, `layer`).
- The tile colliders of a layer are merged into one collider whose AABB spans the whole map, so code dealing with obstacles must use the collider's shape, not its `ColliderAabb` (see `Obstacles::block_collider`). The map uses the `Triangulation` backend, so the collider is filled as in Tiled; the default `Polyline` backend would only keep the outlines.
- To add a new map-driven object: give the tile or object a type in Tiled, then add a match arm in that observer. Types only work for objects: the colliders of a tile layer are merged into one, so a tile's type is lost. Properties that should apply to tiles go on their layer instead, like `blocks_sight` (on a layer, an object or an object's tile), which the same observer turns into `sight::BlocksSight`. The trees are on their own layer "Bäume" for that.
- Layers are 2 apart in z (`TiledMapLayerZOffset`, the default is 100), so upper layers stay below items (z = 5) and units (z = 10); y-sorting moves chunks by up to 1.5 within their layer.
- Collision handling reads Avian's `CollisionStart` messages (via `MessageReader`; Bevy's buffered events are called messages). Only colliders with `CollisionEventsEnabled` emit them, and Avian only reads it when the collider is added to its tree; the observer inserts it after bevy_ecs_tiled added the collider, so Tiled's colliders never emit them (the well doesn't either). The ambush triggers ask the contact graph instead (`Collisions::get(..).is_touching()`).

### Debug controls

- WASD: move the player.
- E / R / T: spawn a small / medium / large enemy at the mouse cursor, asleep until the player sees it.
- G: freeze all enemies or let them go again (also a HUD checkbox).
- F: spawn an item at the mouse cursor, cycling through the item types.
- Left click on an item within reach: pick it up.
- I: open/close the inventory, where items can be dropped again.
- Alt+Enter: toggle borderless fullscreen (a setting, so it is saved).
- Escape: open/close the settings menu, which pauses the game.

The HUD button "Gegner spawnen" spawns a small awake enemy out of sight, "Flowfield" cycles the flow field overlay through the grids (5, 8, 12, 16 px clearance) and off.

The HUD checkbox "Performance" (on by default) shows the frames per second, the frame time and the time of the physics in it, averaged over half a second. The measuring runs either way; the checkbox only decides whether the HUD shows it, which makes the HUD paint again twice a second.

`PhysicsDebugPlugin` draws collider outlines. They start hidden; the HUD checkbox "Kollider" shows them.

The HUD checkbox "Gegner einfrieren (G)" freezes all enemies (`enemy::Frozen`, run condition `enemy::active`): they neither walk, turn nor attack, but can still be hit and pushed.
