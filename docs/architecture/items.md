# Items

The concept is in `docs/items.md`.

Items (`src/items/`, concept in `docs/items.md`): each item is an entity with `Item(ItemId)` and a `Stack` count. Items of the same type always stack, except `Unique` ones (an item with a state of its own; nothing sets it yet), so there is no per-type flag. Item types (name, weight, placeholder color, optional `Effect` when used) come from `assets/items.ron`, hot-reloaded and copied into the `ItemDefinitions` resource, so tests can insert it directly. RON assets like it and `assets/light.ron` use `hot_reload::RonLoader` (implement `RonAsset` with the file's extension), and `hot_reload::loaded_or_modified` tells when to copy them again. On the ground, an item has a `Transform` and is `Pickable`, and `items::render` draws it as a square `Mesh2d` with a `SightMaterial` per type like the enemies, so only its parts in sight are shown; it is picked by Bevy's mesh picking, which only considers `Pickable` entities and the camera with `MeshPickingCamera`, and a click only picks it up while part of it is in sight (`interact::Interactable`, see below). Held, it is hidden (`Visibility::Hidden`), has no `Pickable` and has the relationship `HeldBy(owner)`, mirrored by Bevy in the owner's `Inventory`. The `PickUp` and `DropItem` messages move items between ground and owner, merging stacks of the same type on pickup and splitting stacks when dropping part of them; an item coming to the ground (spawned or dropped) merges into a stack of its type within `MERGE_RADIUS` (`merge_on_ground`, no physics, since items don't move). `UseItem` uses up one held item whose type has an effect (the inventory window's "Benutzen") and sends `ItemUsed { by, effect }`; the items module doesn't apply effects itself, the modules they concern do (combat heals). The player's `items::hotbar::Hotbar` holds an item type per slot (only usable ones, `AssignSlot`); `UseSlot` turns into `UseItem` for the first held item of that type, and a slot keeps its type while none is held. The HUD shows the inventory as auto-sorted tiles right above the hotbar along the bottom edge; dragging between them is built from pointer events, since Blitz has no drag and drop (`docs/items.md`). The hotbar's keys and clicks are handled in `ui::sync_state`, which turns clicks, drops and keys into `ui::put_down` (the one rule for putting a tile or slot down) while the inventory is open, and uses the slot otherwise. `items::Plugin` holds that logic, `items::definitions::Plugin` the asset loading and `items::input::Plugin` the player's input (click to pick up within `PICKUP_REACH`, debug key) and `items::render::Plugin` the look (meshes, materials), so tests only need the first.

**Chests** (`src/objects/chest.rs`) are point objects of type `chest` in Tiled, with an optional property `content` (`apple*3, healing_potion`: item ids with an optional count). The object's entity gets `Chest`, a static 12 × 8 px collider (so it blocks movement and the flow field) and a shadow; its figure (`art/chest.py`) sits on a child holder that keeps it at the units' z, whatever the z of its map layer, and faces the viewer. It shows the first frame of `open` at speed 0 until a click on it (within `chest::REACH`, while in sight) plays `open` once and drops the content as items in front of it. Nothing is saved: a map that is loaded again brings its chests back closed and full.

**Interacting** (`src/interact.rs`): `Interactable { reach, radius }` marks what the player can click to interact with, items on the ground and closed chests, on the entity the pointer hovers (for a figure its root; Bevy's `Hovered` covers its parts). `Interactable::can_interact` is the one check for it: within `reach` of the player's center and in sight. `interact::Plugin` outlines a hovered interactable that has `Pickable` and is in sight: red while the player can interact with it, white while it is out of reach. The outline is a copy of each of its meshes (the item's square, a figure's parts), grown by `OUTLINE_WIDTH` (1 px) around its convex hull, as a child right behind the mesh, so a figure gets one around its silhouette; it is rebuilt only when the state changes, so a figure that turns while outlined keeps the outline of its old direction until then.
